# Architecture decision flow

Use `rally architect` only with a structurally valid current full Report, a confirmed Product Intent Profile, the matching Capability Catalog, and the matching Capability Graph. Prior Init is not required. Treat `stale_input` as a stop condition that requires a fresh Audit or Verify.

Present the complete whole-product Blueprint before requesting any decision confirmation. Keep hard constraints separate from preferences. A hard-constraint conflict is excluded and can never be recommended. Describe recommendations as fit under the confirmed constraints, never as a universal best Provider or as the output of an opaque score.

Preserve the Blueprint's integration compatibility, operational burden, cost drivers and assumptions, data flow and residency, failure domains, Provider concentration, lock-in and exit, duplication, migration cost, Unknowns, trade-offs, assumptions, and reevaluation triggers. A null currency estimate means no current official pricing was reviewed; never invent an exact bill.

Existing implementations default to retain. Replacement requires a positive rationale. After Blueprint confirmation, present each decision independently and submit only the builder's exact `confirm` or `reject` response. Partial completion is resumable and does not imply acceptance of pending or rejected decisions.

The decision flow is read-only. A completed confirmed set returns an Architecture Package bundle with separately versioned Product Intent, Capability Graph, Architecture Record, optional Task Graph, and declared dependency index. Before Init, keep it output-only unless the builder explicitly selects a path; invoke `rally architecture-package --package <bundle.json> --output <selected-path> --json` only for that path. After Init, first invoke `rally architecture-package --package <bundle.json> --json` and present every local-history file in the preview, then repeat with its exact `--resume <token> --confirm confirm` only after explicit approval. Confirmation fails if the package, file list, repository root, or current pointer changed after preview. The append stores shareable Product Intent independently by digest, keeps operational history in the immutable package directory, and shares the history writer lock and current pointer; never stage or commit it. The Manifest remains current intent and never receives the full reasoning history.

Reevaluate package currentness from its exact Report, Product Intent, Catalog, Integration Contract, Provider Knowledge, constraint, and declared decision dependencies. Preserve unrelated records and Evidence when one dependency changes. Treat `needs_reassessment`, `partially_invalidated`, and `superseded` as explicit states rather than rewriting any prior package. No package operation grants Provider write, deployment, or external Executor authority.
